# CLI storage

Status: draft, owned by the CLI. This document describes what aireg keeps on a user's machine and in a project; it is not a specification anyone else implements.

**This is not the file spec.** A registry, the folder, git repository or server holding `registry.json` that artifacts are published to and installed from, is laid out by [`spec/file-spec.md`](../spec/file-spec.md). This document describes only the files aireg keeps around the registries it reads. None of them is a registry, and none is ever checked as one.

## Where aireg keeps things

aireg keeps three folders apart: its own, and one for each scope it installs into.

```
~/.aireg/                  the tool (AIREG_HOME)
  config.yml               accounts, jobs, settings
  credentials.json         tokens aireg stores itself; owner-only (0600)
  bin/aireg                the command on PATH
  cli/<version>/           installed CLI releases
  adapters/                signed adapters, one folder per id and version
  harnesses/               harness files of your own, <id>.json
  state/                   background service: run history (aireg.db), pid file, and on Windows the pipe's name
  run/                     the service's socket, when no folder under /tmp is this user's alone
  logs/                    aireg.log, daemon.log
  leases/                  which process is writing to your user scope
  journals/                what an install in progress has written, one per scope, kept here so a clone cannot supply one
  cache/                   fetched copies of remote registries; deleting it costs a refetch

~/.registry/               your user scope, what -g installs (AIREG_USER_SCOPE)
  manifest.yml
  manifest.lock.yml
  artifacts/

<repo>/.registry/          a project's scope
  .gitignore               written by aireg
  manifest.yml             committed
  manifest.lock.yml        committed
  artifacts/               committed by default
  leases/                  which process is writing to the project; never committed
```

Nothing you install lives in the tool's folder, so the tool can be reinstalled or removed without touching what was installed. `AIREG_HOME` moves the tool's folder and `AIREG_USER_SCOPE` moves your user scope; each is used as given, and neither is worked out from the other. The tool's folder is created on first use, your user scope by the first `-g` command that installs or adds a registry, and a project's `.registry/` by `aireg init` or the first install inside the project.

A scope is not split into XDG config and cache directories because a user should be able to look in one place and see everything aireg installed there.

## Scopes

A command acts on a project, or on your user scope with `-g` (`--user`). The project is the closest folder at or above the working directory that holds `.registry/manifest.yml`, else the root of the git repository around it, the way git finds its repository. Your home folder is never a project: its `.registry/` is your user scope. Outside any project, `aireg add` installs into your user scope and says so. Your user scope needs no setup, so `aireg init -g` is refused.

## A scope's folder

After `aireg add acme/engineering/hello-registry` in a project:

```
.registry/
  .gitignore
  manifest.yml
  manifest.lock.yml
  artifacts/acme/engineering/skills/hello-registry/SKILL.md
.claude/skills/hello-registry -> ../../.registry/artifacts/acme/engineering/skills/hello-registry
.agents/skills/hello-registry -> ../../.registry/artifacts/acme/engineering/skills/hello-registry
```

**`manifest.yml`** is what the scope asks for: the harnesses to install into, the registries it reads, and the artifacts it wants. aireg edits it on `registry add`, `add` and `remove`; after editing it by hand, `aireg install` makes the scope match. An unknown key is refused. Without `harnesses:`, aireg installs into Claude Code and Codex.

```yaml
harnesses:
  - claude
  - codex
registries:
  acme: github.com/acme/ai-registry
artifacts:
  - acme/engineering/skill/lint
  - ref: acme/engineering/skill/pr-review@1.2.0
    harnesses:
      - claude
```

**`manifest.lock.yml`** is what the scope resolved to. aireg writes it on every install and reads it back on the next one. It records each registry once, with the adapter that read it, a key for what was read and, for a git registry, the commit. Each artifact records its registry, version and the content digest that registry published, where the copy lives, a digest of that copy, and every link aireg made for it. A plugin fetched from a repository of its own also records that repository's commit as `revision`, and one that carries hooks, servers or executables records a digest of them as `carried`. Paths are relative to the project, or to your home folder for the user scope, and there are no timestamps, so two branches that add different artifacts merge without a conflict.

```yaml
# Generated by aireg. Do not edit.
version: 1
registries:
  acme:
    source: github.com/acme/ai-registry
    adapter: git
    key: sha256:249c5d8a…
    revision: 8e951d5c7201b235e504660eae9c3d87d58bf814
artifacts:
  pr-review:
    registry: acme
    id: artifacts/engineering/skill/pr-review/1.2.0
    name: pr-review
    kind: skill
    namespace: engineering
    address: artifacts/engineering/skill/pr-review
    content: sha256:8bb984fa…
    version: 1.2.0
    path: .registry/artifacts/acme/engineering/skills/pr-review
    digest: sha256:a321ddc8…
    links:
      - harness: claude
        path: .claude/skills/pr-review
        mode: symlink
```

A registry's `source` is its address, as the manifest declares it. An artifact's `address` is its path inside the registry, and `id` the version folder in it. `content` changes when the registry publishes something new; `digest` changes when someone edits the copy, which is what `aireg status` reports.

**`artifacts/`** holds one copy of each installed artifact, such as `artifacts/<registry>/<namespace>/skills/<name>/` for a skill, and under `artifacts/.projections/` the namespaces aireg lays out for a harness that loads them as a unit, such as a Claude Code plugin. Harness folders link into it, or hold copies with `--copy` or where links are unavailable. A harness that reads its own format, such as Codex for agents, gets a file written from the copy, which the lockfile records as a copy. aireg removes only links the lock lists, so a file it never wrote is never removed. It also never removes or moves a path reached through a symlinked folder inside the project or a harness folder, apart from a link of its own into the scope's `.registry/`, which it unlinks.

**`.gitignore`**, in a project only, is written once and never rewritten. Uncommenting `artifacts/` in it stops committing the installed copies, and `aireg install` then restores them from the lock. aireg never edits the project's own `.gitignore`; `aireg init` warns when that file ignores `.registry/`, since teammates would clone a project that installs nothing.

## Registries

`aireg registry add <address>` records a registry under `registries:` in the scope's `manifest.yml`, keyed by its name. The registry names itself from its `registry.json`; `--as` picks another name. The adapter that reads a registry is worked out from its address unless `adapter:` names one.

| Address | Recorded as | Read by |
|---|---|---|
| `github.com/acme/ai-registry` | the repository | `git`: cloned into `cache/git/`, fetched incrementally after that |
| `https://github.com/acme/ai-registry/tree/main/skills` | the repository, with `ref: main` and `path: skills` | `git`, from that folder at that ref |
| `../acme-registry` | the folder | `local`: read in place; nothing is copied |
| `../skills`, a folder of skills with no `registry.json` | the folder, with `layout: folder` | `local`, read in place and never published to |
| `https://example.com`, a site's web address | the address, with `layout: well-known` | `well-known`, from the site's Agent Skills index, each skill checked against its digest |
| any other address | the address | the adapter `adapter:` names, installed with `aireg adapter install` |

A git registry is fetched into `cache/git/`, one checkout per repository and commit, of which the newest two per repository are kept between runs; each adapter keeps its own folder under `cache/`. An adapter that cannot read a registry in place stages bytes under `cache/.staging/sha256/<digest>/`, keyed by the artifact's content digest and checked against its envelope again whenever they are reused, before only the files the envelope describes are copied into a scope. Every byte aireg reads, from the network, a clone or a local folder, is verified the way the file spec requires before it is installed.

## Credentials and sign-in

`aireg auth login <registry>` stores the registry's token in `~/.aireg/credentials.json` and records the account, its id and registry name, in `~/.aireg/config.yml`. An account is signed in while `credentials.json` holds an entry under its id; `config.yml` never names a token. A token never arrives as an argument: it comes on stdin with `--token-stdin`, from the environment, or through the sign-in the adapter runs. It is never written to a manifest, a lock or `config.yml`.

`credentials.json` holds one plain record per account:

```json
{
  "version": 1,
  "credentials": {
    "acc_7Hq2": {
      "origin": "https://registry.acme.example",
      "type": "bearer",
      "access_token": "<token>",
      "refresh_token": "<token>",
      "expires_at": "2026-10-09T18:00:00Z"
    },
    "acc_9Lm4": {
      "origin": "https://registry.acme.example:8443",
      "type": "api_key",
      "header": "X-Api-Key",
      "value": "<key>"
    }
  }
}
```

| Field | Meaning |
|---|---|
| `version` | `1`. A file with any other version, or any field not listed here, is refused rather than read or rewritten. |
| `credentials` | Keyed by account id, `acc_` followed by letters, digits, `_` and `-`, as in `config.yml`. |
| `origin` | Where the registry was when you signed in: its scheme, lowercase host, and port when it is not the scheme's default, with no path. A git address is its host over `https`. |
| `type` | `bearer`, a token that may expire and be renewed, or `api_key`, a key sent in the named `header`. The registry's adapter decides how a token is sent. |
| `access_token`, `refresh_token` | The tokens of a `bearer` credential. `refresh_token` is present only for a sign-in that expires and can be renewed. |
| `expires_at` | When `access_token` expires, as an RFC 3339 time. In its last minute aireg renews it through the registry's adapter, when the adapter can, and keeps the same `origin`. |
| `header`, `value` | The header and key of an `api_key` credential. |

A token is sent only to its own origin, compared as a browser compares origins. A registry declared at `https://registry.acme.example/team` and one at `https://registry.acme.example/other` share a sign-in; `http://`, another port or another host does not, so a project manifest that declares your registry's name at another address gets no token, and the command stops and says so. A folder has no origin, and git registries read with git's own credentials, so neither takes a token from aireg.

`AIREG_TOKEN_<NAME>`, the registry's name in capitals with other characters as `_`, supplies a token without signing in, which is how CI supplies one; it wins over a stored sign-in. It is sent to the registry of that name the current scope declares, the project's manifest in a project and otherwise your user scope; an address no scope declares under that name gets none. aireg never writes it to disk, and the [daemon](../docs/reference/daemon.md) never inherits it from the command that started it, so a background job uses only stored sign-ins.

aireg creates `credentials.json` readable and writable by its owner alone (`0600`), in a home folder it creates as `0700`, and refuses to read one that is a symbolic link, owned by another user or open to other users, or whose folder others can write to. Every change reads, edits and replaces the file whole under the same cross-process lease aireg takes for a scope, kept in `leases/`, so the CLI and the daemon, which both renew tokens, never lose each other's write, and a crash leaves the old file or the new. Errors about the file name the account and field that are wrong, never a value. `aireg auth logout` deletes the entry. `aireg doctor` warns when other users can read the file.

## Publishing

A publish to a folder registry writes the new version into that folder and updates its `versions.json` and `index.json`, for you to commit. aireg never commits or pushes to a git registry: publish into your clone with `--to <clone>/<namespace>`, then commit and push it with git.
